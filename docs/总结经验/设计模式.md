 对象设计原则：
 | 原则          | 一句话记忆            | 核心关键词         |
| ----------- | ---------------- | ------------- |
| **单一职责原则**  | 一个类只负责一类事情       | **职责单一**      |
| **开放-封闭原则** | 增加功能尽量扩展，不直接改旧代码 | **扩展开放、修改封闭** |
| **里氏替换原则**  | 子类应该能够替换父类使用     | **子类替父类**     |
| **依赖倒置原则**  | 依赖抽象，不依赖具体实现     | **面向接口**      |
| **接口隔离原则**  | 不要让类依赖自己不需要的接口   | **小接口、专用接口**  |
| **组合重用原则**  | 能组合就尽量别靠继承复用     | **组合优于继承**    |
| **迪米特法则**   | 一个对象少了解其他对象      | **最少知识、低耦合**  |
| **迪米特应用**   | 少暴露、少引用、少耦合      | **封装**        |

创建型 Creational
│
├── 单例 Singleton
│     【一个】
│     一个类只有一个实例
│     例：配置中心、日志对象
│
├── 工厂方法 Factory Method
│     【子类决定创建什么】
│     例：创建不同类型的产品
│
├── 抽象工厂 Abstract Factory
│     【一族产品】
│     例：Windows UI / Mac UI
│
├── 建造者 Builder
│     【一步一步构建复杂对象】
│     例：组装一份复杂订单
│
└── 原型 Prototype
      【复制】
      通过复制已有对象创建新对象


结构型 Structural
│
├── 适配器 Adapter
│     【已有类接口不兼容 → 通过适配器转换接口，使其能够复用】
      优点：复用旧代码、解耦接口、兼容不同类
      缺点：增加适配器、适配逻辑复杂、过多会使结构混乱
│
├── 桥接 Bridge
│     【抽象 × 实现分离】
│     例：形状 × 颜色
│
├── 组合 Composite
│     【树形结构】
│     例：文件夹 → 文件
│
├── 装饰器 Decorator
│     【动态增加功能】
│     例：咖啡 + 牛奶 + 糖
│
├── 外观 Facade
│     【统一入口】
│     例：一个接口调用多个子系统
│
├── 享元 Flyweight
│     【共享对象】
│     例：大量相同字符
│
└── 代理 Proxy
      【代替对象】
      例：远程代理、权限代理、缓存代理


行为型 Behavioral
│
├── 命令 Command
│     【把请求封装成对象】
│     → 撤销 / 重做
│
├── 策略 Strategy
│     【算法可替换】
│     → 多种算法自由切换
│
├── 状态 State
│     【对象状态改变 → 行为随之改变；将不同状态封装成独立状态类】
      优点：消除大量 if/else、职责清晰、易扩展
      缺点：类数量多、状态间有耦合、状态切换复杂
│
├── 观察者 Observer
│     【一变多通知】
│     → 发布/订阅
│
├── 模板方法 Template Method
│     【固定流程，部分步骤可变】
│
├── 责任链 Chain of Responsibility
│     【请求沿链传递】
│     → 审批链
│
├── 迭代器 Iterator
│     【遍历集合】
│
├── 中介者 Mediator
│     【对象之间通过中介通信：当多个对象之间相互调用、交互复杂，形成网状耦合时，引入一个“中介者”统一协调它们之间的交互】
      优点：降耦合、集中协调、易维护扩展
      缺点：中介者复杂、易成上帝对象
      | 角色                | 作用              |
      | ----------------- | --------------- |
      | Mediator          | 中介者，负责协调对象之间的交互 |
      | ConcreteMediator  | 具体中介者，实现具体协调逻辑  |
      | Colleague         | 同事对象，参与交互的对象    |
      | ConcreteColleague | 具体同事对象          |


│
├── 访问者 Visitor
│     【对不同对象执行不同操作,对象结构比较稳定，操作经常增加 → 用访问者模式。】
      优点：新增操作容易、职责分离、集中处理
      缺点：新增(元素/对象)困难(增加新的元素类型时，需要修改多个 Visitor。)、破坏封装(Visitor 往往需要访问元素内部数据。)、结构复杂(元素与 Visitor 之间耦合较强。)
      | 角色              | 含义         | 滴滴例子                   |
      | --------------- | ---------- | ---------------------- |
      | Visitor         | 访问者，负责具体操作 | Taxi                   |
      | ConcreteVisitor | 具体访问者      | 具体出租车                  |
      | Element         | 被访问的元素     | Customer               |
      | ConcreteElement | 具体元素       | 某个具体顾客                 |
      | ObjectStructure | 管理一组元素     | Cab Company Dispatcher |

│
├── 备忘录 Memento
│     【保存对象状态】
│     → 恢复历史状态
│
├── 解释器 Interpreter
│     【解释语言/表达式】
│
└── 职责/解释……
