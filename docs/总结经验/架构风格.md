微服务架构：
一、什么是微服务？
定义： 微服务架构是一种将单体应用按照业务能力划分为多个小型、自治服务的架构风格。每个服务围绕特定业务功能构建，可以独立开发、部署和扩展，服务之间通过轻量级通信机制进行协作。

例如，广告投放平台可以拆分为用户服务、广告服务、策略服务和报表服务，各服务分别负责自己的业务功能，并通过 HTTP API 或消息中间件进行通信。
二、适用场景
1. 业务复杂、模块较多： 不同业务模块职责明确，需要独立开发和维护。
2. 业务变化频繁： 各业务模块迭代节奏不同，需要独立发布，减少相互影响。
3. 访问负载差异明显： 某些服务请求量较大，需要单独扩容，避免整体扩容造成资源浪费。
4. 团队规模较大： 不同团队可以围绕业务边界并行开发和交付。
5. 系统需要较强的弹性和故障隔离能力： 希望通过服务隔离、限流、熔断和降级等机制，减少局部故障的影响。
不太适合业务简单、规模较小、团队有限，或者业务模块边界尚不清晰的系统，因为微服务会引入额外的分布式治理和运维成本。
三、优点
1. 松耦合： 服务围绕明确的业务职责划分，通过接口进行交互，降低模块间的直接依赖。
2. 独立部署： 单个服务可以独立开发、测试和发布，减少对整个系统统一升级的依赖。
3. 弹性扩展： 可以根据不同服务的负载情况分别扩容，提高资源利用率。
4. 故障隔离： 配合超时、熔断、限流和降级机制，可以限制局部故障的传播。
5. 技术灵活： 在合理的接口和治理约束下，不同服务可以根据业务需要选择合适的技术方案。
6. 便于团队协作： 不同团队可以围绕独立的业务服务开展工作，提高并行开发效率。
四、缺点
1. 系统复杂度增加： 服务数量增加后，部署、配置、监控和运维工作更加复杂。
2. 网络通信开销： 服务之间通过网络通信，会引入额外延迟，并面临网络超时和通信失败等问题。
3. 数据一致性难度增加： 业务跨越多个服务时，分布式事务和数据同步更加复杂，可能需要最终一致性方案。
4. 故障排查困难： 一个业务请求可能经过多个服务，需要借助分布式链路追踪和集中日志定位问题。
5. 测试与部署成本较高： 服务之间存在接口依赖，需要进行集成测试、兼容性验证和自动化部署。
6. 服务拆分不当会增加耦合： 如果业务边界划分不合理，服务之间频繁调用，反而会增加系统复杂度。

五、考场记忆版
建议你先把下面这段背熟，考场上再结合题目扩展。
微服务架构是一种按照业务能力将应用拆分为多个小型、自治服务的架构风格，各服务可以独立开发、部署和扩展，并通过轻量级通信机制实现协作。

微服务架构适用于业务复杂、模块边界清晰、业务变化频繁、不同模块负载差异较大，以及需要团队并行开发的大型系统。

其优点主要包括：一是服务之间松耦合，便于维护；二是支持独立部署，提高交付效率；三是能够针对不同服务进行独立扩缩容，提高资源利用率；四是结合熔断、限流和降级等机制，可以增强系统的弹性和故障隔离能力。

其缺点主要包括：一是服务数量增加会提高部署和运维复杂度；二是网络通信会引入额外延迟和通信故障；三是跨服务的数据一致性处理更加复杂；四是分布式调用链增加了测试和故障排查的难度。

SOA架构

一、什么是 SOA？
定义： SOA（Service-Oriented Architecture，面向服务的架构）是一种将软件系统的业务功能封装为相对独立、具有明确服务契约的服务，并通过标准化接口实现服务之间协作与复用的架构风格。

例如，企业内部存在用户管理系统、订单系统、支付系统和财务系统，可以将用户查询、订单处理、支付结算等业务能力封装为服务，供多个业务系统调用。必要时，可以通过企业服务总线（ESB）实现协议转换、消息路由和服务集成。
二、SOA 的适用场景
1. 企业系统集成： 企业存在多个独立建设的业务系统，需要实现系统之间的数据交换与业务协同。
2. 异构系统互联： 不同系统采用不同的开发语言、技术平台或通信协议，需要通过统一的服务接口进行交互。
3. 业务能力复用： 多个业务系统需要调用相同的业务功能，避免重复开发。
4. 遗留系统改造： 希望在保留既有系统的基础上，将部分功能封装为服务，逐步实现系统整合。
5. 跨部门业务协同： 多个部门需要组合已有服务，完成跨系统的业务流程。
三、SOA 的优点
1. 服务复用性高： 将公共业务能力封装为服务，供多个应用调用，减少重复建设。
2. 松耦合： 服务通过明确的接口契约交互，调用方不必了解服务内部实现，降低系统之间的直接依赖。
3. 异构系统集成能力强： 通过标准化接口和必要的协议转换机制，实现不同技术平台之间的互操作。
4. 提高系统灵活性： 可以通过组合已有服务快速构建新的业务流程，降低业务调整的成本。
5. 便于渐进式改造： 可以逐步将既有系统的功能封装为服务，降低整体替换系统的风险。
四、SOA 的缺点
1. 服务治理复杂： 需要管理服务目录、接口契约、版本、权限和服务生命周期。
2. 通信开销较大： 服务间远程调用会引入网络延迟，影响系统性能。
3. 集成成本较高： 不同系统的数据模型、接口规范和业务流程存在差异，需要额外的适配和转换。
4. 故障处理复杂： 服务调用可能出现超时、失败和级联故障，需要设计相应的容错机制。
5. 集中式集成设施存在风险： 如果采用 ESB，设计不当可能造成性能瓶颈、中心化依赖和维护负担。
五、考场记忆版
SOA（面向服务的架构）是一种将业务功能封装为相对独立的服务，并通过标准化服务契约实现服务复用与系统协作的架构风格。

SOA 适用于企业内部多个异构系统的集成、公共业务能力复用、遗留系统改造以及跨部门业务协同等场景。

其优点主要包括：一是服务复用性高，能够减少重复建设；二是通过标准化接口降低系统之间的耦合；三是能够实现异构系统之间的互操作；四是可以灵活组合已有服务，支持业务流程调整；五是支持在保留既有系统的基础上进行渐进式改造。

其缺点主要包括：一是服务治理和接口版本管理复杂；二是远程调用会带来额外的网络开销；三是异构系统之间的数据和协议转换增加了集成成本；四是分布式调用增加了故障处理难度；五是采用 ESB 等集中式集成设施时，可能出现性能瓶颈和中心化依赖。

六、和微服务的区别，一句话记住
- SOA： 重点解决企业级业务服务的复用与异构系统集成问题。
- 微服务： 重点强调围绕业务边界拆分服务，实现独立开发、部署和扩展。


事件驱动架构：
一、什么是事件驱动架构？
定义： 事件驱动架构（EDA，Event-Driven Architecture）是一种以事件的产生、传递和处理为核心的架构风格。系统组件通过发布、订阅或响应事件进行协作，事件生产者不需要直接调用每一个事件消费者，从而降低组件之间的耦合。

例如，在智能广告平台中，广告展示后产生一条曝光事件，消息中间件将事件分发给不同的消费者，分别完成曝光统计、用户特征更新和计费处理。
广告展示服务
      │ 发布曝光事件
      ▼
  消息中间件
   ┌──┼──┐
   ▼  ▼  ▼
 统计  特征  计费
 服务  服务  服务


二、事件驱动架构的适用场景
1. 实时数据处理： 需要对用户行为、广告曝光、点击等事件进行实时采集和处理。
2. 异步业务处理： 某项业务完成后，需要触发多个后续任务，但不要求立即返回所有处理结果。（一个生产多个消费）
3. 高并发场景： 通过消息队列缓冲请求，削峰填谷，降低瞬时流量对下游服务的冲击。(写入pika)
4. 多系统协同： 一个业务事件需要通知多个独立系统，例如订单创建后触发库存、物流和通知处理。（一个生产多个消费）
5. 业务扩展频繁： 需要新增事件消费者，而不希望频繁修改事件生产者。
三、事件驱动架构的优点
1. 松耦合： 生产者只需发布事件，无须直接依赖具体消费者，降低模块之间的耦合。
2. 异步处理： 生产者不必等待所有消费者完成处理，可以提高请求处理效率。
3. 可扩展性强： 可以独立增加消费者或调整消费者数量，支持业务功能扩展。
4. 削峰填谷： 消息中间件可以缓冲突发流量，使消费者按照自身处理能力消费消息。
5. 提高系统弹性： 在合理配置消息持久化、重试和故障恢复机制的前提下，可以应对部分消费者暂时不可用的情况。
四、事件驱动架构的缺点
1. 数据一致性复杂： 不同消费者的处理速度不同，数据可能暂时不一致，需要设计最终一致性机制。
2. 消息可靠性要求高： 可能发生消息丢失、重复消费或消息积压，需要处理确认、重试、幂等和死信等问题。
3. 故障排查困难： 事件经过多个组件异步传播，调用链不再直观，需要统一日志和链路追踪。
4. 实时性不确定： 消息积压、网络延迟和消费者处理能力不足可能导致事件延迟。
5. 系统复杂度增加： 需要维护消息中间件、消费进度、重试策略、事件顺序和监控告警等机制。
五、考场记忆版
事件驱动架构（EDA）是一种以事件的产生、传递和处理为核心的架构风格，系统组件通过发布、订阅或响应事件进行协作，降低事件生产者与消费者之间的直接依赖。

事件驱动架构适用于实时数据处理、异步业务处理、高并发流量缓冲、多系统协同以及业务功能需要灵活扩展的场景。

其优点主要包括：一是生产者与消费者松耦合，降低系统模块之间的依赖；二是支持异步处理，提高请求处理效率；三是可以独立扩展消费者，增强系统的可扩展性；四是通过消息缓冲实现削峰填谷；五是结合消息持久化和故障恢复机制，提高系统弹性。

其缺点主要包括：一是异步处理可能导致数据暂时不一致，需要设计最终一致性机制；二是存在消息丢失、重复消费和积压等风险；三是事件传播链路较长，增加故障排查难度；四是消息延迟可能影响业务实时性；五是消息中间件和消费治理增加了系统复杂度。

六、记忆口诀
- 定义： 事件触发、异步协作、生产者与消费者解耦。
- 场景： 实时处理、异步任务、高并发、多系统协同。
- 优点： 松耦合、异步处理、易扩展、削峰填谷。
- 缺点： 一致性难、消息可靠性、排障困难、延迟不确定。
结合你的智能广告平台来理解： 广告曝光请求不必同步等待报表、特征和计费模块全部处理完成，而是先发布曝光事件，由不同消费者异步处理。这正是事件驱动架构的典型应用。


分层架构：
一、什么是分层架构？
分层架构（Layered Architecture） 是将软件系统按照职责划分为若干个层次，每一层承担相对独立的职责，并通过约定的接口与其他层进行交互。

例如，你的智能广告投放平台可以采用这种思路：
- 表现层： 广告运营管理页面，供运营人员配置广告策略。
- 业务逻辑层： 判断广告投放条件、处理策略和推荐逻辑。
- 数据访问层： 查询广告策略、用户特征和推荐结果。
- 数据存储层： 保存广告配置、业务数据和相关记录。

二、分层架构的适用场景
分层架构特别适合以下场景：
1. 业务逻辑相对清晰的管理系统： 如企业管理系统、订单系统、广告运营平台。
2. 系统规模较大，需要职责分离： 不同团队可以分别负责界面、业务和数据访问。
3. 需要长期维护和迭代的系统： 修改界面时，尽量不影响业务规则；更换数据库时，尽量不影响上层业务。
4. 需要复用业务逻辑的系统： 不同表现层可以调用相同的业务服务。
它尤其适合业务职责明确、变化需要分离、维护周期较长的应用。但如果是极度强调低延迟的嵌入式系统，或者业务流程高度动态、跨层交互频繁的系统，就需要谨慎设计层次，避免不必要的调用开销。

三、分层架构的优点和缺点
优点	缺点
职责清晰： 每层承担相对独立的职责，降低系统复杂度。	调用开销： 请求可能需要经过多层，增加调用和处理成本。
易于维护： 修改某一层时，可以减少对其他层的影响。	性能损耗： 层次过多可能导致不必要的转发和数据转换。
便于测试： 可以对各层分别进行单元测试和集成测试。	变更可能跨层： 某些需求涉及多个层，仍需要协调修改。
便于团队协作： 各团队可以按层划分职责和接口。	容易形成紧耦合： 如果上层直接依赖底层实现，分层的优势会被削弱。
技术替换较方便： 可以在接口稳定的前提下替换某一层的实现。	可能出现层次失衡： 业务逻辑可能集中在某一层，或者层层转发却没有实际价值。

这里有一个容易考的点：分层架构的优点是降低耦合、便于维护；缺点是可能增加调用开销，并不意味着采用分层架构就一定性能差。



一、什么是客户端/服务器架构？
客户端/服务器架构（Client/Server，简称 C/S）是一种将系统功能划分为客户端和服务器端的架构风格。客户端负责向用户提供交互界面、发起服务请求，服务器端负责处理请求、执行业务逻辑或管理共享数据，双方通过网络进行通信与协作。

按照客户端的实现方式，常见的形式包括 C/S 架构和 B/S 架构。

注意：B/S 并不意味着客户端完全没有业务逻辑。现代 Web 应用也可以在浏览器中执行复杂的 JavaScript 逻辑，只是通常不需要像传统 C/S 那样安装专用客户端程序。
二、C/S 和 B/S 的适用场景
C/S 架构适用场景
- 交互复杂、性能要求较高： 如专业设计软件、桌面数据分析工具。
- 需要访问本地资源： 如本地文件、设备接口、硬件外设等。
- 需要较强的客户端控制能力： 如游戏客户端、网吧客户端软件。
- 网络环境或业务流程具有特殊要求： 可以根据业务需要设计专用通信协议和本地处理机制。
B/S 架构适用场景
- 企业管理系统： 如 OA、CRM、ERP 和广告运营平台。
- 用户数量较多且分布广泛： 用户可以通过浏览器访问，无须逐台安装专用软件。
- 需要快速迭代和集中维护： 页面和后端服务可以在服务器端统一更新。
- 跨操作系统访问： 在浏览器和运行环境满足要求的情况下，可以减少对特定客户端操作系统的依赖。
三、C/S 和 B/S 的优点与缺点
对比维度	C/S 架构	B/S 架构
客户端部署	通常需要安装专用程序	通常使用浏览器访问
更新维护	可能需要逐台更新客户端	页面和后端通常可集中更新
用户体验	便于实现复杂交互和本地功能	便于快速访问和统一交互
性能	可充分利用客户端计算资源，但取决于设计	涉及浏览器、网络和服务器，复杂计算也可放在客户端执行
跨平台能力	需要适配不同操作系统或运行环境	通常较好，但受浏览器兼容性影响
网络依赖	取决于设计，可支持部分本地处理	通常依赖网络访问 Web 服务
安全管理	客户端分布式部署，版本与终端管理较复杂	便于集中管理，但仍需防范浏览器端和服务端安全风险
服务器压力	取决于业务处理和数据访问的分布方式	业务通常集中在后端，可能增加服务器负载
C/S 架构的主要优缺点
优点：
1. 客户端可以承担部分业务处理，合理设计时能够降低服务器的部分计算压力。
2. 便于实现复杂交互、设备访问和本地资源操作。
3. 可以针对特定业务场景优化客户端性能和用户体验。
缺点：
1. 客户端通常需要安装、升级和维护，部署成本较高。
2. 客户端版本不一致可能导致兼容性和运维问题。
3. 对不同操作系统和设备的适配工作可能较多。
B/S 架构的主要优缺点
优点：
1. 客户端部署简单，用户通过浏览器即可访问。
2. 页面和后端服务便于集中更新和维护。
3. 跨平台访问能力较好，适合分布广泛的用户群体。
4. 便于集中管理权限、业务流程和数据。
缺点：
1. 通常依赖网络和浏览器环境，网络异常可能影响使用。
2. 复杂交互和本地设备访问可能受到浏览器能力限制。
3. 后端服务集中处理请求时，需要关注并发能力、性能瓶颈和可用性。
4. 浏览器兼容性、前端安全和服务端安全均需要专门考虑。

Serverless 架构：
一、什么是 Serverless 架构？
Serverless 架构（无服务器架构） 是一种云计算架构模式，开发人员无需直接管理底层服务器，主要通过云平台提供的计算、存储和其他托管服务来构建应用，由云平台负责资源调度、运行环境管理和弹性伸缩等工作。

需要注意：无服务器并不意味着没有服务器，而是开发人员通常不需要直接管理服务器。

Serverless 通常包含两类核心能力：
- FaaS（函数即服务）： 将业务逻辑编写成函数，由事件或请求触发执行。例如，用户上传文件后自动触发文件处理函数。
- BaaS（后端即服务）： 使用云平台提供的托管后端能力，例如对象存储、数据库、身份认证和消息服务。

云平台负责底层计算资源的分配、运行环境管理及弹性伸缩，具体能力取决于所选服务。

例如，电商平台收到订单后，可以通过消息触发一个云函数，执行订单通知、生成报表或处理图片，无须专门部署一台服务器来持续运行这些任务。
二、Serverless 架构的适用场景
Serverless 特别适合事件驱动、负载波动大、任务执行时间相对较短、希望减少运维工作的业务。
1. 事件驱动处理： 如消息消费、文件上传处理、日志分析和数据清洗。
2. 间歇性任务： 如定时生成报表、周期性数据统计、自动化运维任务。
3. 轻量级 Web 后端： 如 API 接口、用户认证、简单业务服务。
4. 弹性波动明显的业务： 如促销活动、突发流量处理和不定期任务。
5. 快速验证的应用： 开发人员希望减少基础设施搭建工作，快速实现业务功能。
但对于需要长期持续运行、具有复杂状态管理、对稳定低延迟有严格要求，或者需要高度控制运行环境的业务，采用 Serverless 前需要仔细评估。

一、什么是云原生架构？
云原生架构（Cloud Native Architecture） 是面向云计算环境设计的应用架构，充分利用云平台的弹性计算、自动化部署、服务治理和资源编排能力，使应用具备良好的弹性伸缩能力、可维护性、可观测性和故障恢复能力。

云原生不是简单地把传统应用搬到云服务器上，而是根据云环境的特点设计应用及其运行方式。

常见的云原生技术包括：
- 容器化： 使用 Docker 等技术封装应用及其运行环境。
- 容器编排： 使用 Kubernetes 等平台管理容器的部署、调度、扩缩容和恢复。
- 微服务： 将应用按照业务能力拆分为相对独立的服务。
- DevOps 与 CI/CD： 实现自动化构建、测试、部署和持续交付。
- 服务治理与可观测性： 通过服务发现、负载均衡、日志、指标和链路追踪等手段管理系统运行。
- 声明式基础设施管理： 通过配置描述期望状态，由平台协调实际状态。
注意：这些技术是云原生的常见组成或实现方式，并不意味着每个云原生系统都必须采用全部技术。

三、云原生架构的适用场景
1. 大型互联网应用： 如电商、广告平台、社交平台，业务模块多，访问量大且变化明显。
2. 需要弹性伸缩的系统： 如促销活动、流量高峰明显的在线业务，可以根据负载动态调整资源。
3. 持续迭代的业务系统： 需要频繁发布新功能，采用自动化构建、测试和部署提高交付效率。
4. 复杂的分布式系统： 多个服务需要独立部署、扩展和治理。
5. 多环境或多云部署： 需要通过标准化容器和自动化管理，降低不同环境之间的部署差异。
对于规模较小、功能简单、变化较少的系统，采用完整的云原生技术体系可能增加不必要的建设和运维成本。

一、什么是大数据 Lambda 架构？
Lambda 架构（Lambda Architecture） 是一种面向大规模数据处理的架构模式，通过批处理层、速度层和服务层协同工作，兼顾数据处理的准确性、完整性和低延迟要求。

它的核心思想是：利用批处理处理大量历史数据，获得相对完整、准确的结果；利用实时处理快速处理新到达的数据，弥补批处理的时间延迟；最后通过服务层整合两类结果，对外提供查询服务。

三层分别做什么？
- 批处理层（Batch Layer）： 保存不可轻易丢失的历史数据，周期性重新计算数据视图，保证结果的完整性。
- 速度层（Speed Layer）： 处理尚未被批处理结果覆盖的新数据，快速产生近期结果。
- 服务层（Serving Layer）： 将批处理结果与实时结果组合，响应查询请求。
例如，统计今天的广告点击量时，批处理层可能只计算到昨天，而速度层已经计算出今天截至当前时刻的点击量。查询时将两者结合，就能同时获得历史统计和较新的数据。
三、Lambda 架构的适用场景
1. 实时数据分析： 如实时统计网站访问量、用户活跃度和广告点击量。
2. 日志与行为分析： 既需要历史数据的完整计算，也需要及时发现近期行为变化。
3. 金融与风控分析： 需要综合历史交易数据和最新交易事件进行分析，但具体实时性与一致性要求需按业务设计。
4. 物联网数据处理： 同时处理设备历史记录和实时传感器数据。
5. 推荐系统与广告平台： 离线计算用户长期偏好，实时处理用户近期行为。
Lambda 架构尤其适合既要求历史结果较完整，又要求实时响应的场景。如果业务只需要离线分析，批处理架构可能更简单；如果流处理系统已经能满足完整性、准确性和时效性要求，也可以考虑更简单的架构。
四、Lambda 架构的优点和缺点
优点	缺点
兼顾准确性和实时性： 批处理保证历史结果完整，速度层弥补处理延迟。	架构复杂： 需要同时建设和维护两套处理链路。
支持大规模数据处理： 批处理适合海量历史数据的集中计算。	开发成本高： 同一业务逻辑可能需要在批处理和实时处理两端分别实现。
容错与重新计算能力较强： 历史数据保留后，可重新计算批处理结果。	结果整合复杂： 需要处理两条链路的数据重叠、重复统计和时间边界问题。
适应不同的处理需求： 批处理与实时处理可分别优化。	维护困难： 两条链路可能产生结果不一致，需要持续校验。
支持实时查询： 服务层可统一提供批处理和实时处理结果。	资源成本较高： 两套计算链路和存储视图可能带来额外开销。
这里有个重要考点：Lambda 架构并不是简单地把离线计算和实时计算放在一起，关键还在于如何正确合并两条链路的结果。

例如，如果批处理结果已经包含某个时间段的数据，而实时结果也统计了相同时间段，直接相加就会重复计数。因此，系统必须明确数据时间边界、结果覆盖关系及去重规则。

定义：

优点：
1. 兼顾数据处理的准确性、完整性和实时性。
2. 支持海量历史数据的批量处理。
3. 可利用历史数据重新计算结果。
4. 能够适应离线分析与实时分析的不同需求。
缺点：
1. 需要维护批处理和实时处理两套链路，架构复杂。
2. 同一业务逻辑可能需要重复开发。
3. 两条链路的结果整合、去重和一致性处理较复杂。
4. 计算、存储和运维成本较高。
最后记忆
- 批处理层： 负责历史数据，强调完整与准确。
- 速度层： 负责最新数据，强调低延迟。
- 服务层： 整合处理结果，对外提供查询。
一句话概括：Lambda 架构通过“批处理 + 实时处理 + 结果整合”，同时解决历史数据计算和实时数据响应的问题。



一、什么是大数据 Kappa 架构？
Kappa 架构是一种以流处理为核心的大数据处理架构，其核心思想是：统一使用流处理引擎处理实时数据和历史数据，不再像 Lambda 架构那样，同时维护独立的批处理链路和实时处理链路。

Kappa 架构通常以 Kafka 等消息队列作为数据日志，使用 Flink、Spark Streaming 等流处理引擎处理数据，并将结果写入数据库、缓存或查询服务，供上层应用使用。

Kappa 架构的关键不是特定的技术组件，而是实时计算与历史数据重算共用一套流处理逻辑。

例如，当业务规则或计算逻辑发生变化时，可以从持久化日志中重新读取历史事件，再使用更新后的流处理程序重新计算结果，而不必额外维护一套独立的批处理代码。
1. Kappa 架构与 Lambda 架构的区别
对比维度	Lambda 架构	Kappa 架构
核心思想	批处理与流处理并行	统一采用流处理
处理链路	批处理层、速度层、服务层	统一流处理链路及结果服务
历史数据重算	通常通过批处理完成	通过重放历史事件完成
代码维护	可能需要维护两套计算逻辑	通常维护一套核心处理逻辑
主要挑战	两套链路的数据一致性	日志重放、状态恢复与重算成本
记忆要点：Lambda 是“批流双路”，Kappa 是“统一流处理”。

需要注意，Kappa 并不意味着系统完全不能使用离线计算，而是核心数据处理与重算逻辑统一在流处理链路中。

二、Kappa 架构的适用场景
Kappa 架构尤其适合数据持续产生、实时性要求高、需要反复调整计算逻辑的业务。
1. 实时监控与指标分析：实时统计访问量、错误率、交易量等指标，及时发现异常。
2. 实时推荐与智能广告：根据用户最新行为实时更新特征、兴趣偏好或投放决策。
3. 金融风控与反欺诈：持续分析交易事件，识别异常行为并及时采取措施。
4. 物联网与设备监控：处理设备传感器数据，实时监测设备状态和异常事件。
5. 日志分析与行为分析：持续处理系统日志、用户点击流和业务事件，并支持历史日志重放。
但如果业务高度依赖复杂的全量历史扫描、复杂的离线机器学习训练，或者历史数据重放的成本非常高，单纯采用 Kappa 架构未必合适，可能需要保留独立的离线计算链路。
三、Kappa 架构的优点
1. 简化系统架构，降低维护成本。

实时计算与历史重算共用同一套核心处理逻辑，减少重复开发、测试和维护工作，降低批流逻辑不一致的风险。

2. 实时性较好。

数据进入消息队列后即可由流处理引擎持续计算，无须等待批处理任务完成，适合对处理延迟要求较高的业务。

3. 支持历史数据重算。

当业务规则、算法或计算逻辑发生变化时，可以重放持久化日志，重新计算历史结果，减少额外开发批处理程序的工作量。

4. 便于持续迭代。

可以通过部署新版本的流处理程序，对实时数据采用新逻辑，并在具备完整历史日志的前提下重新计算历史结果，支持业务规则和算法持续优化。

5. 有利于统一数据处理标准。

实时处理和历史重算采用相同的核心计算逻辑，能够降低不同处理链路产生口径差异的概率。
四、Kappa 架构的缺点
1. 历史数据重算成本较高。

重算大量历史数据需要重新读取日志并执行计算，可能占用大量计算、存储和网络资源，耗时也可能较长。

2. 对消息日志的持久化能力要求高。

必须根据业务需要保留足够长时间的历史事件，并保证数据能够可靠读取和重放。如果日志已过期或数据缺失，就可能无法完整重算历史结果。

3. 流处理逻辑和状态管理较复杂。

涉及窗口计算、有状态处理、事件时间、乱序数据、检查点和状态恢复等问题时，开发与运维仍有较高复杂度。

4. 不适合所有类型的离线分析。

对于复杂的全量数据扫描、长周期历史统计、复杂数据关联及大规模模型训练，专门的批处理引擎往往更合适，强行统一为流处理可能导致资源利用率和开发效率下降。

5. 重算期间可能影响在线服务。

历史数据重放可能与实时任务争抢计算资源，还需要妥善处理新旧结果切换、重复事件、结果覆盖以及状态初始化等问题。

五、结合智能广告投放平台理解
以你熟悉的智能广告投放平台为例：
- 实时链路：用户产生点击、启动游戏等行为事件，经 Kafka 进入 Flink，实时计算用户特征或行为指标，将结果写入 Redis，供广告投放接口读取。
- 历史重算：当特征计算规则调整时，从持久化日志中重放历史行为，使用新版本的 Flink 作业重新计算特征。
- 在线服务：广告投放接口读取 Redis 中的特征或计算结果，结合广告策略完成投放决策。
不过，你目前的平台还使用 Spark 进行离线计算和模型训练。因此，更准确的描述是：平台采用离线计算与实时计算相结合的混合架构，实时行为处理部分可以借鉴 Kappa 的设计思想。 仅仅同时使用 Spark 和 Flink，并不能说明整个系统就是 Kappa 架构。
